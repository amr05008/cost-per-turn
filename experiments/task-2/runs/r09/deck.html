Internal PM Session

Go get yourself a
personal agent

Always-on AI assistants changed how I use the internet.
Here's my setup, what I learned, and why you should build one too.

Open with the thesis directly: of everything I've experimented with this past year, personal agents are the most useful, the most interesting, and now the foundation I layer every new project on top of.

Frame for PMs: this isn't a coding talk. It's about a new interaction pattern — an always-on assistant you reach from your phone, anywhere — and what it means for how people will expect products to work.

Timing: ~1.5 min here.

Why

The most useful thing I've built this year

An always-on assistant, reachable from my computer, phone — wherever — has changed how I use the internet.

  • Captures every idea, question, and task the moment I have it
  • Turns throwaway thoughts into researched, high-fidelity plans
  • Information flows to me instead of me chasing it
  • It's the foundation I now layer new projects on top of

Key point: the value isn't any single feature — it's availability. The agent is always there, so the friction of "capturing a thought" drops to zero.

Before this, I'd email ideas to myself, scribble on paper, or dump into Notion — mostly forgotten. Now silly ideas actually become plans I execute, delegate, or deliberately archive.

PM angle: think about what happens to your product's engagement metrics when a user's agent is the one "using the internet" on their behalf.

The Setup at a Glance

Two agents, one shared brain, one Discord

🥧 Pi Pi

Lives on a Raspberry Pi 5. The personal assistant — ideas, questions, plans, tasks.

💻 Agent M1

Lives on an old laptop. More power, more storage, more responsibility — investigates issues, reviews PRs.

🧠 Shared memory

One memory layer, synced through GitHub every ~4 hours. If one agent learns something, the other picks it up.

💬 Discord front door

Reached entirely from Discord — phone, laptop, anywhere. Runs within a Claude Max plan + API costs for side projects.

This is the architecture slide — keep it quick. Two always-on machines (cheap / free hardware I already had), one memory layer synced via GitHub, and Discord as the single interface.

Emphasize how un-glamorous the hardware is: a $80 Raspberry Pi and a retired laptop. The barrier to entry is low.

Cost: fits inside the $100/mo Claude Max plan (not the $200 tier). Side projects like twitter-watcher use API keys with variable cost.

The Plumbing

Claude Channels: the agent lives where the chat is

  • Channels wire a Claude Code session to a messaging platform — Discord, in my case
  • The agent listens for new messages (DMs or channel posts) via the messaging API
  • The plugin forwards the message to the always-on session; the agent replies right in the chat
  • Result: the agent lives on an always-on machine, but I reach it from anywhere

Mechanism in one breath: message arrives in Discord → plugin forwards it to the Claude Code session running on the Pi → agent crafts a reply → posts back in the chat.

Contrast with my first attempt, Openclaw: my first always-on agent that learned my preferences, but I was constantly repairing it. Channels + Claude Code has been far more stable.

The important shift: I'm no longer tied to my desk or an SSH session to talk to my agent.

The First Agent

Pi Pi: from stray thought → researched plan

  • I have my best ideas biking or walking the dog — my phone is the capture device
  • Voice-to-text straight into Discord. Don't be precious about typos — Opus/Sonnet parses the intent
  • The killer workflow: the agent doesn't just start building — it researches, writes a markdown plan, commits it to git
  • I pick the plan up from my laptop later and execute when I'm ready

This is the single most useful workflow I've found. Tell the story: idea strikes on a walk → rambling voice memo to Pi Pi → by the time I'm home, there's a researched plan in a plans folder, committed to git.

Then I triage: execute it myself, delegate it to the agent, or archive it. Either way it's a decision, not a forgotten note.

PM angle: the "capture → structured artifact" pipeline is the product insight. The agent turns low-fidelity input into high-fidelity output asynchronously.

Organizing the Work

Discord channels = job segmentation

#questions — random questions
#reminders — schedule & receive reminders
#daily-briefing — weather + articles from authors I follow
#signals — daily twitter-watcher digests
#inbox-alerts — flagged emails needing attention
#to-do — assign agent tasks
#fitness — Zwift race analysis via Strava MCP
#glutenornot — uptime + Sentry errors for my app

Start with just #general. Add channels one at a time, per project, as needed.

I started with a single #general channel and layered new channels on one at a time — mostly per project. Strongly recommend starting small.

Each channel is effectively a scoped job queue with its own context. The channel structure is the product surface — no app to build, no UI to design.

PM angle: channels-as-jobs is a dead-simple information architecture your users already understand.

The Behavior Change

Information flows to me now

  • Inbox-watcher: reviews, catalogs, and prioritizes forwarded email. It caught my Rosalía-at-MSG concert being rescheduled and flagged it as action-required — no inbox-zero chasing.
  • Twitter-watcher: checks the topics and accounts I care about, decides what's worth reading, posts a weekday summary to #signals. Twitter signal without Twitter.
  • Agents compose: I asked Pi Pi to research how people use Claude Tag to expand on a #signals post — without ever logging into Twitter.

The headline: I used to check email incessantly and absentmindedly. I still do sometimes, but far less — task-dedicated agents took over the watching.

The Rosalía story is the concrete win: a rescheduled concert buried in email, caught and flagged as needing action. That's the difference between monitoring and drowning.

The composability point matters most: agents that post to channels + my personal agent present in the same channels = I can task my agent to go deeper on anything, from my phone.

How To Set It Up

Learn from my mistakes: just use tmux

  • Any always-on machine works — a Raspberry Pi is cheap and low-power; an old laptop is free
  • I tried a systemd service first — it broke repeatedly. Now: a tmux session wrapped in a while true loop, so the agent respawns if it crashes
  • Enable user lingering (loginctl enable-linger) so tmux survives SSH disconnects
  • Use Tailscale for a secure private network between your devices — a "secure conference room" off the public internet
claude --channels plugin:discord@claude-plugins-official

The systemd route broke multiple times in the first few hours. With guidance from Opus I switched to tmux + while-true loop and it's been solid. Just go with tmux.

Connect Discord as an MCP plugin with the one-liner on screen (also findable via the /plugins Discover tab).

Give the agent tools, skills, and MCPs exactly like a normal Claude Code session — SSH in, attach the tmux session, configure as usual. Both my agents can read across my GitHub repos.

Scaling Up

One agent → two agents

  • Agent M1 (old laptop): more power, more storage, room to experiment with local LLMs
  • More responsibility: read/write on my GlutenOrNot app, Sentry + PostHog MCPs — detects issues, reviews and submits PRs, with guardrails on autonomous action
  • Shared memory via GitHub: each agent syncs every ~4 hours and reads across the same memory — one brain(ish)
  • Real moment: M1 debugged why my app wasn't showing in the EU (unsigned forms) while Pi Pi handled finance questions — concurrently, from my phone

Why a second agent: the laptop had spare power and storage, and I wanted to tinker — including offloading some tasks to local models. The Pi is still going strong.

The trust gradient is deliberate: Agent M1 got permissions I wasn't willing to give the Pi, but with guardrails on what it can do autonomously.

Describe the PR-review moment: Agent M1 reviewing a PR that Pi Pi created to debug API failures — agents collaborating with each other.

Hard-Earned Lessons

Memory, security, tinkering

  • Real memory, not just a session. Everything in memory loads into context — less is more. Only critical rules + active-project facts load every session; the rest is on-demand or archived.
  • Take security seriously. Channel agents get far less tool access than my desktop sessions. They see untrusted input (random emails, Sentry errors) — never act on embedded instructions. Audit permissions after week one. Hardware keys on important accounts.
  • You will tinker. Not constant repair, but not zero. ~3 months: two restarts on the Pi, weekly /clear of the 1M-token context. If Discord goes quiet, check the tmux session — auth probably dropped.

Memory: if it grows too big, the agent misses the important stuff in the noise. Design the load-every-session set ruthlessly.

Security: think in blast radius. Every allow-listed permission widens it. Grant more as trust is earned — otherwise the agent DMs you constantly for permission.

Maintenance reality check: it's ~once-every-few-weeks upkeep, not daily firefighting. Be honest with the audience about this.
