What I actually run

The whole setup, in four lines

  • Two always-on agents. "Pi Pi" on a Raspberry Pi 5, "Agent M1" on an old laptop.
  • One shared memory layer, synced between them through GitHub roughly every 4 hours.
  • Reached entirely from Discord. Phone, laptop, anywhere — no SSH required.
  • Runs inside a Claude Max plan — the $100 tier, not the $200. Side projects add API cost.

Scaling up

One agent became two,
sharing one brain

Why a second machine

More power for research tasks, far more on-device storage, and a path to trying local LLMs. The Pi is still going strong — I just wanted to tinker.

More trust, deliberately

Agent M1 gets read/write on my GlutenOrNot app plus Sentry and PostHog MCPs, so it can investigate issues and open PRs — with guardrails on what it may do alone.

Memory syncs to GitHub about every 4 hours, so what one learns the other picks up.
One recent evening, from my phone: M1 found why the app wasn't live in the EU (unsigned forms) while Pi Pi handled finance questions.

Learning 01

Give it a real memory,
not just a session

Everything in memory loads into context every single session. Let it grow unchecked and the agent drowns the important stuff in noise.

What works: load only critical rules and facts about active projects by default. Everything else is called on demand, or archived so it can't cause confusion.

Less is more. Treat the memory layer as a product you curate, and build it together with the agent.

Learning 02

Take security seriously:
mind the blast radius

  • Channel agents get far less access than my desktop sessions. Every extra tool, MCP and allow-list entry widens the blast radius.
  • These agents read untrusted input — random emails, Sentry errors. They must never act on instructions buried in that content, or approve new access without me.
  • Audit after a week or two. Every allow-list permission, every channel the agent can see. Hardware keys on accounts that matter.
  • Then loosen up, on purpose. Once the blast radius was small, I granted more — otherwise it DMs you to read a repo.

Backup slide

If you go build one:
the setup that actually held

  • Any always-on machine. A Pi 5 is cheap and sips power; an old laptop is fine. A machine that sleeps defeats the point.
  • Use tmux, not systemd. My systemd service broke repeatedly within hours. A tmux session wrapped in while true respawns the agent every time.
  • Enable lingering: loginctl enable-linger <user>, or the session dies when you close SSH.
  • Tailscale for a private tailnet — makes SSHing in easy.
  • Add tools the normal way: SSH in, attach to tmux, wire up skills and MCPs as usual.
