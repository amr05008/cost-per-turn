The big idea

Information comes to me.
I stop going to get it.

I used to wade through the internet — inbox, Twitter, tabs — hoping to find what mattered.

Now the things I care about arrive in a channel, already filtered and summarized.

Before: check email incessantly and absentmindedly. Scroll Twitter to stay current. Ideas die in Notion.

After: a short daily brief, an alert when an email actually needs me, a plan waiting in git for the idea I had on a bike ride.

This is the slide to slow down on. If they remember one thing, it's the direction of flow flipping.

  • Frame it as a behavior change, not a tech change: the pull-to-push flip is what reduced my compulsive email checking.
  • PM hook: "every product we own assumes the user comes to us. What breaks when an agent comes instead?"
  • Don't over-claim — say honestly "I still check email sometimes, just much less."

  • Mechanism in one sentence: the plugin polls the messaging API, forwards the message to the always-on session, the agent replies in the chat.
  • Setup war story (keep to 20 seconds): systemd broke repeatedly in the first hours; tmux + while true has been rock solid. "Learn from my mistakes, just go with tmux."

Workflow that stuck #1

researched plan out

It doesn't start building. It investigates first.

Markdown plan in git
Committed to a plans folder, waiting for me at my laptop.

Before: ideas got emailed to myself, scribbled on paper, or buried in Notion — and forgotten. Now more of my silly ideas become plans good enough to actually build, delegate, or confidently throw away.

This is my single most useful workflow. Say that out loud.

  • Emphasize "research then plan, don't build." The artifact is a reviewable markdown plan, not surprise code.
  • The unlock is capture at the moment of the idea — biking, walking the dog — before it evaporates.
  • Note the underrated outcome: higher-fidelity plans make it much easier to *kill* bad ideas. PMs feel that one.
  • If time is tight, cut the "before" list and just say "these used to die in Notion."

The organizing trick

One Discord channel per job

#questions random asks #reminders schedule + receive #daily-briefing weather, authors I follow #signals twitter-watcher output #inbox-alerts emails that need me #to-do assign agent tasks #fitness Strava / Zwift analysis #glutenornot uptime + Sentry errors

Started with just #general and questions. Added one channel at a time, mostly per project. Start small.

  • The point isn't the channel list — it's that channels give each agent job a clean scope, an audience of one, and a place to look later.
  • Strong advice: don't design the whole taxonomy up front. Add a channel when a job earns one.
  • Pick 2–3 channels to describe, not all 8. #daily-briefing and #inbox-alerts land best with this audience.
  • Bonus mechanic: my personal agent sits in the same channels as the webhook-posting agents, so I can reply "go deeper on this" in-thread.

so I don't have to

INBOX-WATCHER

Triage instead of refresh

Two Gmail accounts forward here. It reviews, catalogs, assigns priority, and pings #inbox-alerts only when I'm needed.

It caught that my Rosalía show at MSG had been rescheduled — no inbox-zero chasing required.

TWITTER-WATCHER

The signal without the site

Tracks chosen accounts and topics, judges whether the discussion is worth reading, posts a short weekday summary to #signals.

I researched a brand-new Claude feature via my agent — without ever logging into Twitter.

  • Lead with the Rosalía story — it's concrete, human, and instantly legible. Something important happened in email and I found out without looking.
  • The generalizable pattern: an agent per stream of untrusted, high-volume input, with an explicit "does this deserve a human?" evaluation step.
  • Twitter-watcher's real goal: "I wanted the information from Twitter without spending time on Twitter."
  • Then the compounding bit: external agents post via webhook, and my personal agent is already in the room to expand on anything.

Scaling up

Two agents, working in parallel

  • M1 got the bigger job: read/write on my GlutenOrNot app, plus Sentry + PostHog MCPs. It can detect issues and submit PRs, with guardrails.
  • Shared memory in GitHub: both agents sync back every ~4 hours and read the same store — one learns, the other picks it up.
  • Real moment: from my phone, M1 debugged why my app wasn't visible in the EU while Pi Pi worked my finance questions — at the same time.
2agents, one brain (ish)
~4hmemory sync interval between them
  • Why a second agent at all: more compute for research, more local storage, and a runway to experiment with local models. Also — I had the laptop lying around.
  • Trust is tiered, not binary: the laptop agent gets write access and prod monitoring; the Pi agent doesn't. Match tool access to the machine and the job.
  • Nice image to mention: M1 reviewing a PR that Pi Pi opened. Agents reviewing each other's work with me as the approver.
  • The parallelism story is the "aha" — two workstreams progressing while I'm away from a computer.

Three hard-won learnings

Memory, blast radius, upkeep

01 — MEMORY

Give it a memory, not a session

Everything in memory loads into every session, so less is more. Only critical rules and active projects load by default; the rest is fetched on demand or archived.

02 — SECURITY

Shrink the blast radius

My channel agents get far less access than my desktop sessions. They read untrusted input — emails, Sentry errors — so they must never act on instructions embedded in content, or grant new access without me.

03 — UPKEEP

Expect to tinker

Not zero overhead. Check in every few weeks. 2 restarts in 3 months; I clear the 1M-token context about weekly. Silent failure looks like "agent stopped replying."

  • Memory: the failure mode is a bloated memory file where the agent misses the important stuff in the noise. Work with the agent to prune it.
  • Security is the slide to be most sober on. Prompt injection via forwarded email is a real, live threat surface here. Also: hardware keys on important accounts.
  • Concrete recommendation: after week one or two, audit every allow-list permission and every channel the agent can see.
  • Honest nuance: I loosened permissions over time, because constant "can I read this repo?" DMs were worse than the risk.
  • Upkeep fix, if asked: SSH in, attach tmux, restart Claude or re-auth, /clear.
