Internal PM session

Go get yourself a personal agent

Of everything I explored this year, a personal agent was the most useful, the most interesting — and it's now the foundation I build every new project on top of.

Open with the pitch, not the architecture: I'm going to argue that every PM here should build a personal agent. Not because it's novel — because it's the single most useful thing I've built this year, and because it's now the base layer for all my side projects.

Frame it for PMs: this is about leverage on your own attention and ideas, not about being an engineer. Then promise the shape of the talk: what I run, what changed, how to build one, what I learned.

At a glance

The setup in four bullets

  • Two always-on agents — "Pi Pi" on a Raspberry Pi 5, "Agent M1" on an old laptop
  • One shared memory — synced between them through GitHub every ~4 hours
  • Reached from Discord — phone, laptop, anywhere; voice-to-text on the go
  • Cost — fits in a Claude Max plan ($100 tier), plus API costs for side projects

This is the whole system on one slide. Emphasize how unglamorous the hardware is: a $80-ish Pi and a retired laptop. No servers, no cluster.

Key PM point: the interface is Discord — an app they already use. The "product surface" of my agent is a chat window on my phone.

Cost: set expectations early. This runs inside a Claude Max subscription; the extra projects layered on top use API keys with variable cost.

The core idea

Always-on, reachable from anywhere

An agent that lives on an always-on machine, wired to a messaging channel — so you can reach it from wherever you are, not just at your desk.

Claude Channels connects a Claude Code session to Discord; the agent listens for messages and replies right in the chat.

Explain the mechanism briefly: the Claude Channels plugin has the agent in a Claude Code session listen to a messaging API (DMs or channel posts in Discord), forward the message to the always-on session, and reply in the messenger. So "Pi Pi" is just... always there.

Context: my first taste of this was Openclaw — an always-on agent that learned and recalled my preferences. It was frustrating to operate, but it proved the value of persistence. Channels gave me the same shape on infra I trust.

For PMs: the unlock is reachability + persistence. An assistant you can only use at your desk is a tool. One that's always reachable starts to feel like a teammate.

The first agent

Capture every idea, turn it into a plan

  • Dump thoughts from anywhere — voice-to-text on my phone, mid-walk, mid-bike ride
  • The agent researches and writes a plan in markdown, saved to a plans folder, committed to git
  • I execute later from my laptop — build it, delegate it back to the agent, or archive it

Before: ideas went to email, paper scraps, or Notion — usually forgotten. Now they become high-fidelity plans.

The single most useful workflow: idea → research → markdown plan → git. The agent doesn't just start building; it plans, which means I can review, hand it back, or throw it away cheaply.

Practical tip: don't be precious with voice-to-text. With Opus or Sonnet as the underlying model, the agent parses messy dictation fine. My best ideas come while biking or walking the dog — the phone is the capture device.

Contrast with the old behavior: emailing myself, scribbling notes, Notion graveyards. The delta isn't capture — it's that ideas come back as plans of much higher fidelity, so more of them actually get executed.

Structure

Discord channels = job segmentation

  • #questions / #to-do — random questions; assign the agent tasks
  • #reminders / #daily-briefing — scheduled nudges; daily weather + reads from authors I follow
  • #signals — daily summaries from my twitter-watcher agent
  • #inbox-alerts — an agent flags emails that need attention
  • #fitness / #glutenornot — Zwift race analysis via Strava MCP; uptime & Sentry alerts for my app

Start with one #general channel. Add channels one at a time, mostly per project, only as needed.

Design principle for PMs: I segment jobs by Discord channel. Each channel has one purpose, which keeps context clean for both me and the agent.

How it evolved: I started with a single #general and added channels slowly, one at a time, mostly per project. Strongly recommend that path — starting with ten channels is a recipe for noise.

Skim the list for flavor rather than reading every item: the point is the pattern — each recurring job in my life got its own lane — not the specific channels.

The behavior change

Information flows to me now

  • Inbox-watcher reviews, catalogs, and prioritizes forwarded email; alerts me in #inbox-alerts
  • Twitter-watcher follows topics and accounts, judges what's worth reading, posts a weekday summary
  • My personal agent sits in the same channels — I can task it to dig deeper on anything that shows up

Example: the agent caught that my Rosalía concert at MSG was rescheduled — before I ever saw the email. I checked email less; zero inbox-chasing required.

This is the slide about how my internet usage actually changed. I used to check email incessantly and absentmindedly. Now the information I care about flows into Discord instead of me wading out to find it.

Tell the Rosalía story — it lands well: the inbox-watcher caught a rescheduled MSG concert in a forwarded email and flagged it as action-needed, with no inbox-zero effort on my part.

Second example: twitter-watcher. I wanted Twitter's information without Twitter's time cost — it posts a short summary each weekday into #signals. And because my personal agent is present in the same channels, I've asked Pi Pi to go research a #signals item (how people were using Claude Tag) and bring the answer back — without me ever logging into Twitter.

Scaling up

From one agent to two

  • Agent M1 lives on an old laptop — more power for research, more storage, room to try local LLMs
  • More trust, more tools — read/write on my GlutenOrNot app, Sentry + Posthog MCPs, reviews/submits PRs with guardrails
  • One brain (ish) — both agents sync memory to GitHub every ~4 hours and read the same shared memory
  • Parallel help — M1 debugged an EU availability issue while Pi Pi worked through finance questions, all from my phone

Why a second agent: not because the Pi failed — it's still going strong — but because I had the hardware and wanted more compute, storage, and a place to experiment with local models.

Trust gradient matters: I granted M1 more responsibility than the Pi — write access to my app, Sentry and Posthog MCPs — with explicit guardrails on what it can do autonomously. There's a nice moment where M1 reviews a PR that Pi Pi opened to debug API failures.

Memory sharing: each agent syncs its memory to GitHub every ~4 hours, both read the shared layer, so learning transfers between them. End with the parallel-session anecdote — two agents, two problems, one phone.

Build your own

Setup: learn from my mistakes

  • Hardware — any always-on machine; a Pi is cheap and low-power, but an old laptop works
  • Run it right — skip systemd (it broke repeatedly); use a tmux session wrapped in a while true loop so the agent respawns on crash or /exit
  • Keep it alive — loginctl enable-linger so tmux survives SSH disconnects; Tailscale for a private tailnet between devices
claude --channels plugin:discord@claude-plugins-official

Always-on is the whole point — an agent on a machine that sleeps is an agent that disappears.

The mistake to save people from: I first ran the session as a systemd service with auto-restart, and it broke multiple times within hours. Opus itself suggested tmux + a while-true loop; that has been solid. (Fun aside: I'd first heard of tmux via Steve Yegge's "Gas Town" writeup.)

Two operational details: enable user lingering or tmux dies when you disconnect SSH; and Tailscale — a private tailnet, "secure conference room" off the public internet — makes reaching the Pi and other devices trivial. Tools/skills/MCPs are configured exactly like a normal Claude Code session: SSH in, attach tmux, configure. My agents have GitHub access so they can read across all my repos.

Learnings

What I'd tell anyone starting out

  • Give it a real memory, not just a session. Less is more — everything in memory loads every session; keep only critical rules and active-project facts, archive the rest.
  • Take security seriously. Agents see untrusted inputs (random email, Sentry errors). Minimal tool access, allow-list permissions, audit after week one or two, hardware keys on important accounts.
  • Expect to tinker. Not zero overhead: ~2 restarts in 3 months, plus a weekly /clear of the 1M-token Opus context window.

Memory: work with your agent to design it. Because all memory loads into context each session, bloat means the agent misses the important stuff in the noise. Ours loads only critical rules and active-project facts; everything else is recall-on-demand or archived.

Security: every tool, skill, MCP, and allow-list permission grows the blast radius. Agents process untrusted content, so they must never act on instructions embedded in that content or self-approve new access. Start minimal, audit the allow-list and Discord channel access after a week or two, then widen deliberately — I did, once constant permission DMs became the bigger annoyance than the risk.

Tinkering: much lower maintenance than Openclaw was, but not zero. Silent failures look like Discord going quiet — SSH in and restart Claude, or re-auth. Budget expectations: two restarts in three months, one weekly /clear.

  • Your turn — start small: one old machine, one Discord channel, one job
