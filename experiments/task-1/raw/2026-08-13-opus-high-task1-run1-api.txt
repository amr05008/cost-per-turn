  Top 3 insights

  1. The app's most common answer is "I don't know." 71% of all scans return 
  caution.

  ┌─────────┬───────────┬───────────┬───────────┐
  │ verdict │  barcode  │    ocr    │   total   │
  ├─────────┼───────────┼───────────┼───────────┤
  │ caution │ 205 (73%) │ 100 (67%) │ 305 (71%) │
  ├─────────┼───────────┼───────────┼───────────┤
  │ safe    │ 52        │ 37        │ 89 (21%)  │
  ├─────────┼───────────┼───────────┼───────────┤
  │ unsafe  │ 23        │ 13        │ 36 (8%)   │
  └─────────┴───────────┴───────────┴───────────┘

  On the barcode path this is partly structural: 62 of 280 successful barcode 
  scans (22%) had had_ingredient_data=false — Open Food Facts (47) or UPCitemdb
  (15) returned the product but no ingredient text, so the verdict was
  caution/low by construction. Those are logged as successes but are
  functionally non-answers. Add the 26 not_found misses and ~29% of barcode 
  attempts end with no real verdict. A further 102 scans had ingredients and
  still came back caution/medium — that's a prompt-calibration question, not a
  data-coverage one, and the two need separating.

  2. OCR failure halved after 1.4.1, and the residual failures are small images 
  — including a client-bug signature.

  OCR ocr_failed rate: 23.2% before 2026-08-01 → 10.0% after (29/125 → 6/60).
  The capture-assist work landed.

  The remaining failures are strongly size-correlated — this is the image_kb
  question your 1.4.2 note was waiting on, and it now has an answer:

  - median image_kb: 179 KB on failure vs 403 KB on success
  - 53% of failures were <200 KB vs 9% of successes; P(fail) ≈ 58% under 200 KB
  vs 6% over 400 KB
  - ocr_chars = 0 on every failure — Vision returned nothing at all, not "too
  little"

  And of the 6 post-Aug-1 failures, three came from one iOS user at exactly 36.0
  KB each — identical byte sizes on three retries. That's not user framing; a
  36 KB frame retried to the same size looks like the capture pipeline emitting
  a degenerate (blank/black/underexposed) image. Worth connecting to the torch
  on-device check still outstanding from 1.4.1.

  3. OCR failure is terminal; barcode failure isn't — and one of the dead-ends 
  was almost certainly Apple's reviewer.

  ┌──────────────────┬─────┬─────────────────────────┬──────────────────────┐
  │     failure      │  n  │ recovered w/ a success  │   was user's last    │
  │                  │     │         ≤10 min         │      event ever      │
  ├──────────────────┼─────┼─────────────────────────┼──────────────────────┤
  │ ocr_failed       │ 35  │ 6 (17%)                 │ 7                    │
  ├──────────────────┼─────┼─────────────────────────┼──────────────────────┤
  │ not_found        │ 26  │ 19 (73%)                │ 4                    │
  │ (barcode)        │     │                         │                      │
  └──────────────────┴─────┴─────────────────────────┴──────────────────────┘

  A barcode miss is an annoyance users route around. An OCR failure ends the
  session 83% of the time. Layer on retention: 80 of 97 users (82%) were active 
  on exactly one day, while 4 users with 5+ active days drove 34% of all events
  — so the one-shot first impression is doing nearly all the acquisition work,
  and OCR is where it breaks.

  Most pointed instance: on 2026-07-28, the day after v1.4.1 was tagged, a
  device geolocated to Cupertino logged 6 events, all ocr_failed, and nothing 
  else. Timing plus location plus the pure-failure pattern makes App Review the
  strong read (it's an inference from IP geo, not proof). The build passed
  anyway, but a reviewer's entire experience of the OCR path was six consecutive
  failures.

  3 action items to prioritize

  1. Instrument why an image is degenerate, then fix the 36 KB case. Add
  capture-side properties to the OCR path — mean luminance, torch on/off,
  camera-ready elapsed ms, and pre/post-compression byte size — and a client
  scan_failed reason=blank_frame when a frame lands under a size/luminance
  floor. The privacy invariant is safe here: these are all counts and device
  state, never content. Then reproduce the 36 KB triple-retry directly; it
  smells like the same torch/settle race that 0a360a0 ("Apply torch after a
  settle window") was chasing. Cheapest interim mitigation: refuse to upload and
  re-prompt when the encoded frame is under ~100 KB, rather than spending a
  Vision call to learn it's blank.

  2. Split the caution bucket into "no data" and "hedged," and treat them 
  differently. Right now they're indistinguishable in the funnel. Two moves: (a)
  for the 22% of barcode hits with no ingredient text, stop presenting a
  caution verdict card and instead route straight to "we found this product but
  have no ingredient list — scan the label" with a one-tap handoff to OCR; (b)
  audit a sample of the 102 had-ingredients/medium-confidence cautions against
  test-cases/ to find out whether the prompt is genuinely uncertain or
  reflexively hedging. Only (b) can tell you if 71% caution is honest
  calibration or a product that's afraid to commit — and given the app's whole
  value is a decision at the shelf, that's the highest-leverage unknown you
  have.

  3. Get real retention measurement before optimizing for it. The 82% one-day
  figure is built on distinct_id = SHA-256 of client IP, which fragments a
  returning user across networks — it under-counts return visits by an unknown
  amount, so you can't currently tell a retention problem from a measurement
  artifact. A rotating install-scoped anonymous ID generated on-device (no
  account, no PII, stored in AsyncStorage alongside Recents) would fix this
  without touching the privacy posture — though it is a privacy-policy and App
  Store label review, so run the privacy-claims-check pass before shipping it.
  Related smaller cleanup: 12 events in the window still land as platform: 
  unknown, which is quiet attribution noise on top.

  Two caveats on the above. scan_failed only began emitting in the week of
  2026-07-05, so failure trends can't be compared to June. And the
  pre/post-Aug-1 split is a proxy for the 1.4.1 rollout — v1.4.1 was tagged
  07-27 but I don't have its actual App Store release date, so the true
  inflection could sit a few days either side.
